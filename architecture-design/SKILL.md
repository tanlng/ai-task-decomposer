# architecture-design

## 何时使用
- 设计架构
- 方案设计 / 系统设计
- 模块拆分
- DDD 划分
- 数据流分析
- 设计扩展点
- 判断是否应该演化现有结构

## 集成原则
1. 不新增平行的 SDD Skill。
2. SDD 是 Architecture Skill 的前半段，DDD 是后半段。
3. PRD 负责定义要什么，SDD 负责定义系统怎么协作，DDD 负责定义业务规则归谁负责。
4. 先做 SDD 再做 DDD；没有系统职责、接口和约束收敛前，不直接讨论聚合或分层落点。
5. 低复杂度任务允许轻量化 SDD，但不能省略对职责、数据流和约束的判断。

## 默认工作顺序
1. 校验 PRD / 需求约束是否稳定。
2. 产出 SDD：系统目标、约束、模块协作、数据流、接口、异常路径、性能与可观测性要求。
3. 产出 DDD：限界上下文、实体 / 聚合、领域服务、领域事件、规则归属。
4. 映射实现：目录、模块 owner、扩展点、测试与发布影响。

## 默认输出
1. 结论摘要
2. 约束分析
3. SDD 系统设计
4. DDD 领域划分
5. 模块 / 服务设计
6. 数据流 / 时序 / 状态说明
7. UML / Mermaid 图
8. 风险与演进路径
